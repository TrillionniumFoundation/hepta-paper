# Canonical convergence qualification subject

This document defines the evidence boundary for the Global Development Plan 1.1 canonical-development convergence candidate.

## Exact-subject rule

A convergence decision is valid only for one tuple containing:

- repository ID and full name;
- pull-request number;
- base ref, commit and tree;
- head ref, commit and tree;
- tested prospective merge commit, tree and ordered parents;
- the complete manifest-authenticated producer workflow and required-context set;
- every visible run attempt, job, executed step and retained artifact used by qualification;
- the current independent review decision bound to that same tuple.

Changing any tuple member invalidates the decision. A review, workflow result, artifact or status derived before a base retarget or head update does not transfer.

## Convergence scope

The current source candidate combines the canonical campaign/resource and qualification line with bounded planning-source components and the repository-owned no-effect provider technical sandbox. Source qualification may establish internal consistency and reproducibility only. It does not establish external provider identity, credential custody, target-host isolation, protected replay, production deployment or authority transfer.

## Admission requirements

Ordinary integration into the canonical development branch requires all of the following on the unchanged exact subject:

1. every registered producer and aggregate workflow is terminal-success with non-empty execution evidence;
2. required-check, raw collection, normalized projection, V1, V3 and V2 artifacts are mutually consistent and live-current;
3. static architecture, complete portable tests, Rust checks, documentation and supply-chain gates pass;
4. the prospective merge tree is the tree actually reviewed and qualified;
5. a reviewer distinct from the implementation author approves the current subject;
6. no unresolved blocking conversation or current change request remains.

Integration is source-only and non-activating. It must not modify work-item completion, provider, writer, release, submission, portal, production or external-authority fields merely because source admission succeeds.

## External gates

The following remain independently controlled even after source integration: authoritative provider implementation and credentials; source-route acceptance; protected private replay; target host and GPU controls; destructive storage recovery and soak; separated roles; KMS/HSM and WORM custody; shadow/canary and rollback; writer-generation transfer; and final production/release/submission authorization.

Fixtures, repository-administrator statements, local tests and portable sandbox receipts cannot manufacture those facts.
