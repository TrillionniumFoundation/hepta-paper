# Native pristine schema rebind

`schema_rebind.rs` implements the incumbent version-2 reserve, finalize and observe protocol. It reuses the existing schema-transition hashes, typed validation and receipt verifiers. The separately configured authority signs with its supplied Ed25519 key; this module creates no key, deployment qualification or writer permission.

The owner calls `handle`, `activate_finalized` and `inspect` inside its existing SQLite IMMEDIATE transaction. The module never starts a nested transaction, reads a configuration file or opens a business database. `handle` normalizes JSON numbers through the existing Node-compatible contract before dispatch.

Reserve requires a genuinely signed completed initial version-1 schema transition, a matching complete source configuration, all ten source heads at sequence zero, unchanged instance/schema correspondence, and no mutation rows. Even aborted mutations prevent a pristine rebind. It computes the exact target configuration hash from the complete actual source configuration, changing only the requested writer-manifest and database-scope fields. The contract still requires the scope to equal the incumbent scope. Initial genesis signatures are checked against their historical writer manifest, with the same actual authority key and scope, so a second legitimate pristine rebind remains possible.

Finalization persists signed installation evidence and keeps the source heads and source metadata in `reserved`. It does not activate the target. A source-configuration restart returns `false` from `activate_finalized`; target observation remains unavailable. After the storage owner verifies the actual persisted public-key hash, an actual reload of the exact signed target configuration can activate the single matching finalization. Activation verifies both stored signatures and contracts, the complete source/target configuration hashes, authority/key/scope identities, unchanged source heads and absence of mutations before atomically replacing all ten heads and metadata. It accepts historical correctly finalized evidence after the reservation has expired; a still-unfinalized reservation cannot activate.

Expired reservations renew only with identical request and unchanged source preimage. Renewal changes the reservation identifier and receipt hash, invalidating installation requests built against the old reservation. Finalization at the expiry boundary is rejected. Stored receipt tampering, ambiguous or missing evidence, wrong target settings, wrong key and unexpected heads are rejected.

The incumbent refuses **every unfinished backup row**, including expired ones, during initial reserve and renewal. This port preserves that refusal and applies it during finalize/activation too. No evidence is deleted or migrated automatically. Recovery of abandoned backup rows therefore remains an explicit separate policy decision. The owning runtime checks its current persisted configuration and actual key identity inside each transaction, so an old source runtime cannot continue issuing receipts after another instance activates the target.

Tests use an independently supplied fixture key and real SQLite transactions. They obtain initial genesis through the actual native version-1 handler, exercise an actual file close/reopen for activation and a second pristine rebind, verify signatures, reject altered keys/configuration/evidence/heads/mutations and a genuine unfinished backup, test expiry renewal, and inject a metadata failure to prove that all ten preceding head updates roll back. These tests establish the local authority state machine; they do not certify a production deployment or replace external acceptance.
